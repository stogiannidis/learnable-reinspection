# Datasets

Reference for every corpus wired into the training and evaluation pipelines.
The canonical registry lives in `src/data/registry.py`; the preparation logic
lives in `src/data/prepare_training_data.py`; per-dataset loaders live in
`src/data/refcoco.py` (Stage 1) and `src/data/spatial_dataset.py` (Stage 2).

On-disk layout (relative to `data_root`, default `/data/datasets`):

```
<data_root>/<dataset_name>/
  train.json           # or train.jsonl for vsr
  val.json
  images/              # or a symlinked directory into a shared image pool
```

Hydra config groups `stage1_datasets` and `stage2_datasets` let you pick any
subset at launch time (see `src/configs/stage{1,2}_datasets/*.yaml`).

## Stage 1 — Referring-expression grounding

All Stage-1 datasets produce samples in the `RefCOCODataset` schema:
`{image, expression, bbox=[x, y, w, h] in absolute pixels, image_w, image_h}`.

### refcoco, refcoco+, refcocog
- **Task.** Classic referring-expression grounding (UNC / UMD splits).
- **Images.** COCO `train2017` — symlinked from `/data/datasets/coco/train2017/`.
- **Prep.** Not regenerated by `prepare_training_data.py`; expected to be
  materialized on disk already (folder name must match the registry entry).
- **Default in mix.** Yes.

### grefcoco
- **Task.** Generalized referring expressions (empty- and multi-target refs).
- **Source.** `FudanCVL/gRefCOCO` on HuggingFace Hub
  (`grefs(unc).json` + `instances.json`).
- **Images.** COCO `train2017` — same pool as refcoco/+/g.
- **Prep.** `prepare_grefcoco()`; downloads the two JSONs via
  `huggingface_hub.snapshot_download` (the parquet split is broken — mixed
  polygon/RLE `segmentation` column — so we bypass `datasets.load_dataset`).
  Requires `--coco_image_dir` (default `/data/datasets/coco/train2017`).
- **Default in mix.** Yes.

### vg_grounding
- **Task.** Region-description grounding from Visual Genome.
- **Source.** Local VG dump at `--vg_input_dir` (default `/data/datasets/vg`)
  containing `region_descriptions.json` and `image_data.json`.
- **Images.** VG `VG_100K/` and `VG_100K_2/` — copied into the dataset's
  `images/` subfolder.
- **Prep.** `prepare_vg_grounding()`.
- **Default in mix.** Yes.

### grit
- **Task.** Web-scale grounded image-text pairs (from Kosmos-2's GRIT release).
- **Source.** HuggingFace-streamed pairs; images fetched from arbitrary web
  URLs via `urlretrieve`.
- **Images.** Unique per pair — no sharing with any other dataset. Stored in
  `grit/images/` after download.
- **Prep.** `prepare_grit()`, throttled by `--grit_max_samples`. Slow; network
  bound.
- **Default in mix.** Yes.

## Stage 2 — Spatial VQA

Stage-2 datasets produce `{image, question, answer}` samples; `build_spatial_dataset`
concatenates any subset under a common `data_root`.

### vsr
- **Task.** Visual Spatial Reasoning (binary true/false over 66 English
  spatial relations).
- **Source.** Public VSR release (`train.jsonl` / `val.jsonl`).
- **Images.** **COCO** — VSR is built on COCO images, shared with the Stage-1
  RefCOCO family. The loader expects them under `vsr/images/` (symlink to the
  COCO pool is standard).
- **Default in mix.** Yes.

### gqa_spatial
- **Task.** Spatial subset of GQA questions.
- **Source.** Filtered from `/data/datasets/gqa/`.
- **Images.** GQA image pool — **shared with the VG family**, because GQA's
  images are themselves a subset of Visual Genome (COCO+Flickr sources).
  Practically: GQA images are in GQA's own folder, but the underlying photos
  overlap with `vg_grounding`, `vg_spatial`, and the VG portion of
  `cambrian_spatial`.
- **Default in mix.** Yes.

### clevr_spatial
- **Task.** Synthetic spatial VQA on CLEVR-style scenes.
- **Source.** **Generated locally** by `prepare_clevr_spatial()` — no
  download. Tunable via `--clevr_num_scenes`, `--clevr_canvas_size`,
  `--clevr_max_qa`.
- **Images.** Rendered on the fly; **unique to this dataset**.
- **Default in mix.** Yes.

### vg_spatial
- **Task.** Synthetic spatial QA pairs mined from Visual Genome
  `relationships.json`.
- **Source.** Local VG dump (same as `vg_grounding`), capped by
  `--vg_max_samples` (default 200 000).
- **Images.** VG `VG_100K/` + `VG_100K_2/` — **shared with `vg_grounding`
  and the VG branch of `cambrian_spatial`**, and overlapping with
  `gqa_spatial`'s underlying pool.
- **Default in mix.** Yes.

### rel3d
- **Task.** Rel3D 3D spatial relations benchmark.
- **Source.** Expected raw dump at `rel3d/raw/`; rendered into `rel3d/images/`.
- **Images.** **Unique** — no overlap.
- **Default in mix.** **No** (needs annotations on disk).

### cambrian_spatial
- **Task.** Cambrian-10M spatial subset; a mix of GQA-style and VG-style
  questions.
- **Source.** Primary: HuggingFace stream `nyu-visionx/Cambrian-10M`. Often
  broken mid-shard; the loader has `--cambrian_source {fallback,auto,hf}`.
  Fallback synthesizes the mix from local GQA + VG.
- **Images.** Mixed — **GQA images** for the GQA branch and **VG images**
  (VG_100K/VG_100K_2) for the VG branch. In fallback mode the images are
  copied from those local pools.
- **Default in mix.** **No** (HF stream reliability).

## Image-source sharing matrix

Datasets sharing the *same* image pool can safely be concatenated without
image-duplicate concerns flipping train/val splits — and conversely, if you
split by image rather than by sample, you must do it across the whole group.

| Image pool                 | Datasets that use it                                                                 |
|----------------------------|--------------------------------------------------------------------------------------|
| COCO `train2017`           | `refcoco`, `refcoco+`, `refcocog`, `grefcoco`, `vsr`                                 |
| Visual Genome (`VG_100K*`) | `vg_grounding`, `vg_spatial`, `cambrian_spatial` (VG branch)                         |
| GQA (subset of VG photos)  | `gqa_spatial`, `cambrian_spatial` (GQA branch); overlaps the VG pool at the photo level |
| Unique per-dataset         | `grit` (web), `clevr_spatial` (synthetic), `rel3d`                                   |

Notes:
- GQA's images are drawn from the same COCO+Flickr photos that Visual Genome
  indexes, so at the *photo* level `gqa_spatial` overlaps with the VG group
  even though the served image files sit in a different directory.
- `vsr` overlaps COCO at the *photo* level with the RefCOCO family; overlap
  with COCO-based validation splits (e.g. refcocog val) is possible and
  should be accounted for if you care about strict image-level holdout.
- `grit` images are downloaded from arbitrary URLs; practical overlap with
  COCO or VG is effectively zero but not formally guaranteed.

## Preparing data

```bash
python -m src.data.prepare_training_data \
  --output_dir /data/datasets \
  --datasets all \
  --coco_image_dir /data/datasets/coco/train2017 \
  --vg_input_dir   /data/datasets/vg
```

Pass any subset of `{grit, rel3d, cambrian_spatial, clevr_spatial, vg_spatial,
vg_grounding, grefcoco}` to `--datasets`. The three RefCOCO variants, `vsr`,
and `gqa_spatial` are expected to already be on disk in the registry-specified
folders.

## Selecting datasets at train time

Via Hydra config groups:

```bash
python -m src.train stage=stage1 stage1_datasets=grefcoco_only
python -m src.train stage=stage2 stage2_datasets=benchmarks_only
```

Or by overriding the raw list:

```bash
python -m src.train stage1_dataset_names='[refcoco,grit]'
python -m src.train stage2_dataset_names='[vsr,gqa_spatial]'
```

Available presets:
- `stage1_datasets/`: `default`, `all`, `refcoco_only`, `grefcoco_only`,
  `grit_only`, `no_grit`
- `stage2_datasets/`: `default`, `all`, `clevr_only`, `vg_only`,
  `benchmarks_only`

Leaving the list as `null` (the `default` preset) falls back to
`registry.stage{1,2}_defaults()`, which is every entry with `default=True`
in `src/data/registry.py`.

## Training experiments

Each experiment is **one Hydra config** under `src/configs/experiment/<name>.yaml`.
All training goes through [`src/scripts/run_train.sh`](../src/scripts/run_train.sh),
which is the single entrypoint for both Stage-1 and Stage-2. All non-secret
configuration (`OMP_NUM_THREADS`, `HF_HOME`, experiment names, …) is hardcoded
in that script. Kubernetes jobs only inject `HF_TOKEN` and `WANDB_API_KEY` from
the secret store.

| Experiment YAML (`src/configs/experiment/`) | Backbone   | Stage | Notes                                    |
|----------------------------------------------|------------|-------|------------------------------------------|
| `s1_qwen.yaml`                               | Qwen2.5-VL | 1     | no-GRIT mix (default pipeline Stage-1)  |
| `s1_qwen_full.yaml`                          | Qwen2.5-VL | 1     | + GRIT (ablation)                        |
| `s1_internvl.yaml`                           | InternVL3  | 1     | no-GRIT mix                              |
| `s1_gemma4.yaml`                             | Gemma 4    | 1     | grounding aux loss                       |
| `s2_qwen.yaml`                               | Qwen2.5-VL | 2     | default Stage-2 datasets                 |
| `s2_qwen_full.yaml`                          | Qwen2.5-VL | 2     | + rel3d, cambrian_spatial (ablation)     |
| `s2_internvl.yaml`                           | InternVL3  | 2     | default Stage-2 datasets                 |
| `s2_gemma4.yaml`                             | Gemma 4    | 2     | default Stage-2 datasets                 |
| `s2_internvl_grounding.yaml`                 | InternVL3  | 2     | from grounding Stage-1 checkpoint        |
| `s2_internvl_focal.yaml`                     | InternVL3  | 2     | from focal Stage-1 checkpoint            |
| `s2_internvl_kl.yaml`                        | InternVL3  | 2     | from kl Stage-1 checkpoint               |

**Full pipeline** (Stage-1 → Stage-2 in one job): `run_train.sh` runs Stage-1,
finds the latest `models/…/stage1/epoch_*/reinspection_module.pt`, passes it
to Stage-2. Logs: `logs/pipeline_<s1>__<s2>.log`, `logs/<s1>.log`,
`logs/<s2>.log`. **Stage-1 only**: set `REINSPECTION_EXPERIMENT_STAGE2=` empty.

### Submitting

Edit the `# ── Configuration` block in `src/scripts/run_train.sh` to set
`REINSPECTION_EXPERIMENT` and `REINSPECTION_EXPERIMENT_STAGE2`, then:

```bash
kubectl apply -f k8s/train.yaml
```

Dedicated per-backend jobs (no config editing required):

| Job | Runs |
|-----|------|
| `k8s/train.yaml` | Default pipeline (edit `run_train.sh` for different experiment) |
| `k8s/stage1.yaml` | `s1_internvl` (Stage-1 only) |
| `k8s/stage2.yaml` | `s2_internvl` (Stage-2 only) |
| `k8s/stage1_gemma4.yaml` | `s1_gemma4` (Stage-1 only) |
| `k8s/stage2_gemma4.yaml` | `s2_gemma4` (Stage-2 only) |
| `k8s/stage2_ablation.yaml` | Stage-2 ablation (edit experiment name in command) |

**Pipeline mode** passes `stage1_checkpoint` automatically; the Stage-2
experiment YAML's default path is not used for fresh S1→S2 runs.

### Changing settings

All training settings live in the Hydra experiment YAML. The k8s manifest is
only for compute (GPUs, node selector, image, secrets, volumes). Edit
`src/scripts/run_train.sh` to change which experiment runs by default.

### Adding a new experiment

1. Add `src/configs/experiment/my_exp.yaml`:
   ```yaml
   # @package _global_
   defaults:
     - override /backend: qwen25vl
     - override /stage: stage2
     - override /stage2_datasets: vg_only

   stage1_checkpoint: models/qwen25vl/stage1/epoch_4/reinspection_module.pt
   wandb_run_name: my_exp
   experiment_name: my_exp
   ```
2. Set `REINSPECTION_EXPERIMENT=my_exp` in `src/scripts/run_train.sh` and
   `kubectl apply -f k8s/train.yaml`.

### Running locally (no k8s)

```bash
# Use script defaults (s1_qwen → s2_qwen pipeline)
bash src/scripts/run_train.sh

# Override experiment inline
REINSPECTION_EXPERIMENT=s1_internvl REINSPECTION_EXPERIMENT_STAGE2= bash src/scripts/run_train.sh

# Stage-2 only, explicit checkpoint
REINSPECTION_EXPERIMENT=s2_qwen REINSPECTION_EXPERIMENT_STAGE2= bash src/scripts/run_train.sh
```

Extra arguments are passed through to `deepspeed --module src.train` as Hydra
overrides (e.g. `REINSPECTION_EXPERIMENT_STAGE2= bash src/scripts/run_train.sh
stage1_checkpoint=models/...`).

## Evaluation benchmarks

Evaluation is separate from training: benchmarks are held-out test sets only.
They are registered in `BENCHMARK_CONFIGS` in `src/evaluate.py:76` and
selected via the `benchmarks` field in `src/configs/stage/eval*.yaml` (or
`--benchmarks` on `src/data/prepare_benchmarks.py`). Each benchmark lives at
`<data_root>/<name>/test.json` (or `.jsonl`) with an `images/` folder.

Default suite (7 benchmarks, all present under `/data/datasets/`):

| Benchmark     | Task                                                        | Images                                      | Format     |
|---------------|-------------------------------------------------------------|---------------------------------------------|------------|
| `vsr`         | Binary T/F over 66 English spatial relations                | COCO                                        | `.jsonl`   |
| `gqa_spatial` | Spatial subset of GQA questions                             | GQA (photo-overlaps with VG)                | `.json`    |
| `whatsup`     | Controlled L/R/above/below probes on staged objects         | Bespoke photographs — no overlap            | `.json`    |
| `3dsrbench`   | 3D spatial reasoning benchmark                              | Bespoke — no overlap                        | `.json`    |
| `mindcube`    | Mental rotation / 3D cube reasoning                         | Synthetic — no overlap                      | `.json`    |
| `blink`       | BLINK visual-perception subset (spatial relations portion)  | Mixed web — effectively no overlap          | `.json`    |
| `srbench`     | Spatial Reasoning Benchmark                                 | Bespoke — no overlap                        | `.json`    |
| `qspatial`    | Quantitative spatial (distance/height/width with reference) | Bespoke photographs — no overlap            | `.json`    |
| `embspatial`  | Embodied egocentric MCQ (above/below/L/R/close/far)         | Indoor embodied scenes — no overlap         | `.json`    |

### Overlap with training data

- `vsr` images are drawn from COCO, i.e. the same photo pool as the Stage-1
  RefCOCO family. If you train on `refcoco*` / `grefcoco` and evaluate on
  VSR, some *photos* will be seen during training even though the *tasks*
  (grounding vs. T/F VQA) are different. Report this caveat in result tables.
- `gqa_spatial` (eval) and `gqa_spatial` (train) are drawn from GQA; ensure
  you respect GQA's official train/val/test splits when preparing the train
  side. The eval `test.json` should come from GQA's held-out split.
- `whatsup`, `3dsrbench`, `mindcube`, `blink`, `srbench`, `qspatial`, and
  `embspatial` have no image overlap with any training dataset in
  `registry.py`.

### Choosing benchmarks

```bash
# Full default suite:
python -m src.evaluate stage=eval checkpoint_dir=...

# Subset:
python -m src.evaluate stage=eval benchmarks='[vsr,whatsup,3dsrbench]' checkpoint_dir=...
```

The three `eval*` stage configs (`eval.yaml`, `eval_focal.yaml`,
`eval_grounding.yaml`) all share the same default list; override per-run as
needed.
